# 📘 PROJETO 1 – Planejamento de um Produto - Do problema ao primeiro Sprint

## 🧩 PROBLEMA

Uma empresa de tecnologia procura novas ideias de produtos que possam **resolver problemas reais do cotidiano**.

Porém, existe uma regra:

> A equipe não pode começar pensando em um aplicativo.
> 

Primeiro, precisa descobrir **qual problema vale a pena resolver**.

Depois, deverá entender quem sofre com esse problema e planejar uma primeira versão de uma solução.

### O desafio da equipe

Vocês deverão escolher um **problema real**, conversar com possíveis usuários e transformar esse problema em uma proposta de produto.

No final, a equipe deverá sair da atividade com:

- um problema real identificado;
- usuários definidos;
- uma solução proposta;
- uma primeira versão do produto;
- um conjunto de tarefas;
- um objetivo para a primeira Sprint.

# 👥 ORGANIZAÇÃO DAS EQUIPES

Será formado grupo de 4 alunos. Com 33 alunos, teremos: **8 grupos de 4 alunos e 1 grupo de 5 alunos**.

### Sugestão de funções

**Responsável pelo Produto**

- organiza a visão da solução;
- mantém o foco no usuário.

**Responsável pela Tecnologia**

- avalia como a solução poderia ser construída;
- identifica dificuldades técnicas.

**Responsável pela Experiência**

- pensa na facilidade de utilização.

**Responsável pela Organização**

- controla tarefas e tempo.

**Responsável pela Comunicação**

- registra decisões e apresenta o resultado.

> As funções são apenas para organizar o trabalho. Todos devem participar das decisões.
> 

# 🔎 Etapa 1 – Encontrando um problema real

A equipe deverá observar problemas que realmente existem.

Podem procurar problemas relacionados a:

- escola;
- comunidade;
- comércio local;
- transporte;
- educação;
- serviços;
- pequenos negócios;
- vida dos estudantes;
- tecnologia.

### ⚠️ Regra principal

O grupo **não pode começar pela tecnologia**.

Evite:

> "Vamos criar um aplicativo de..."
> 

Comece por:

> "Existe um problema em..."
> 

## 📌 Exemplos

### Problema

> Pequenos comerciantes têm dificuldade para organizar pedidos recebidos pelo WhatsApp.
> 

### Problema

> Estudantes têm dificuldade para acompanhar trabalhos e prazos de diferentes disciplinas.
> 

### Problema

> Pessoas têm dificuldade para encontrar determinados serviços disponíveis na comunidade.
> 

O objetivo é encontrar problemas que **realmente possam ser investigados**.

# 👤 Etapa 2 – Pensar no usuário

Agora o grupo deverá definir:

### Quem possui o problema?

Exemplo:

> Pequenos comerciantes que recebem muitos pedidos pelo WhatsApp.
> 

### Como essa pessoa resolve atualmente?

> Anota em papel ou tenta organizar as mensagens manualmente.
> 

### Qual é a principal dificuldade?

> Perde pedidos e tem dificuldade para acompanhar o que já foi entregue.
> 

## 🗣️ Validação rápida

**Sempre que possível**, os alunos deverão conversar com **pelo menos uma pessoa que realmente tenha relação com o problema**.

Pode ser:

- outro aluno;
- professor;
- funcionário;
- familiar;
- comerciante;
- profissional da comunidade.

Não é necessário internet.

### Perguntas sugeridas

```
Você realmente enfrenta esse problema?

Como resolve isso atualmente?

O que é mais difícil?

Com que frequência isso acontece?

O que você gostaria que fosse diferente?
```

📌 O aluno deve **escutar**, e não tentar convencer a pessoa de que sua ideia é boa.

# 🧠 Etapa 3 – Definindo o produto

Depois de entender melhor o problema, a equipe deverá propor uma solução.

Agora sim podemos perguntar:

> **Que produto ou serviço poderia resolver esse problema?**
> 

A equipe deverá definir:

### Nome provisório do produto

### Problema que resolve

### Usuário principal

### Solução

### Principal benefício para o usuário

# 🧩 Etapa 4 – Produto ou projeto?

Agora a equipe deverá identificar:

### Qual é o produto?

É aquilo que continuará sendo utilizado pelo cliente.

### Quais serão os projetos necessários?

São trabalhos específicos realizados para construir ou melhorar o produto.

## 📌 Exemplo

### Produto

> Sistema para organização de pedidos de pequenos comerciantes.
> 

### Projetos

```
Projeto 1 → Criar primeira versão
Projeto 2 → Implementar cadastro de produtos
Projeto 3 → Criar painel de pedidos
Projeto 4 → Melhorar experiência do usuário
```

A equipe deverá fazer o mesmo com sua solução.

# 📋 Etapa 5 – Criando o primeiro Backlog

Agora a equipe deverá transformar a ideia em **tarefas concretas**.

Exemplo:

```
[ ] Entender como os pedidos são recebidos
[ ] Definir informações necessárias
[ ] Criar modelo de organização dos pedidos
[ ] Testar com um comerciante
[ ] Coletar feedback
```

As tarefas devem ser pequenas o suficiente para que a equipe consiga entender exatamente o que precisa fazer.

# 🎯 Etapa 6 – Planning da primeira Sprint

Agora será realizada uma **mini Planning**.

A equipe deverá escolher quais tarefas consegue realizar primeiro.

### Regra

A equipe não deve escolher tudo.

Deve perguntar:

> **Qual é o resultado mais importante que conseguimos alcançar primeiro?**
> 

## Exemplo

### Objetivo da Sprint

> Criar e testar uma primeira forma de organizar pedidos de pequenos comerciantes.
> 

### Tarefas escolhidas

```
[ ] Entender o processo atual de pedidos
[ ] Criar uma organização simples dos pedidos
[ ] Testar a solução com um usuário
```

As demais tarefas ficam para depois.

# 👨‍💻 Etapa 7 – Participação do programador

A equipe deverá responder:

> **Se esse produto fosse desenvolvido por uma equipe de tecnologia, como o programador poderia contribuir?**
> 

Não basta responder:

> "Programando."
> 

A equipe deve pensar em contribuições como:

- avaliar viabilidade;
- sugerir uma solução técnica;
- identificar riscos;
- simplificar funcionalidades;
- pensar na experiência do usuário;
- propor uma primeira versão possível.

# 💻 Etapa 8 – Criando o repositório do produto no GitHub

Cada equipe deverá criar um **repositório no GitHub** para registrar o desenvolvimento do produto.

O repositório será o espaço oficial onde a equipe irá documentar o projeto durante as próximas etapas.

### 📌 Nome do repositório

O nome deve ser simples e relacionado ao produto.

Exemplos:

```
organiza-pedidos
estuda-facil
agenda-comunitaria
meu-servico
```

Evitar nomes como:

```
projeto-final
trabalho-escola
teste123
```

## 📁 Estrutura inicial

O repositório deverá começar com pelo menos:

```
nome-do-produto/
│
└── README.md
```

O arquivo `README.md` será a **página de apresentação do produto**.

# 📝 Etapa 9 – Criando o README do produto

O grupo deverá criar o README contendo:

```markdown
# Nome do Produto

## Problema

Qual problema estamos tentando resolver?

## Público

Quem enfrenta esse problema?

## Solução

O que estamos propondo?

## Objetivo da Sprint

O que queremos conseguir nesta primeira Sprint?

## Tarefas

- [ ] Tarefa 1
- [ ] Tarefa 2
- [ ] Tarefa 3

## Equipe

- Nome – Função
- Nome – Função
- Nome – Função
```

📌 **Importante:** o README não deve ser apenas uma descrição genérica. As informações precisam representar o problema que a equipe realmente investigou.

# 📋 Etapa 10 – Criando as Issues

Agora a equipe deverá transformar as tarefas da Sprint em **Issues do GitHub**.

Por exemplo:

### Issue #1

**Investigar como os comerciantes recebem pedidos**

### Issue #2

**Definir informações necessárias para cada pedido**

### Issue #3

**Criar primeira solução para organização dos pedidos**

### Issue #4

**Testar solução com usuário**

## 🎯 Por que utilizar Issues?

Porque no mercado de tecnologia as equipes utilizam sistemas de gerenciamento de tarefas para acompanhar o trabalho.

O GitHub pode ser utilizado não apenas para armazenar código, mas também para:

- organizar tarefas;
- registrar problemas;
- acompanhar atividades;
- documentar decisões.

# 👥 Etapa 11 – Organização da equipe

Cada integrante deverá ter uma responsabilidade definida.

No README, registrar:

| Integrante | Responsabilidade |
| --- | --- |
| Aluno 1 | Produto |
| Aluno 2 | Tecnologia |
| Aluno 3 | Pesquisa/usuário |
| Aluno 4 | Organização |
| Aluno 5 | Documentação |

As funções podem mudar durante o desenvolvimento.

📌 O objetivo não é criar cargos definitivos, mas **organizar o trabalho da equipe**.

# 🔄 O projeto continua

O ponto mais importante é que o projeto **não termina depois dessas aulas**.

O repositório criado agora será utilizado durante as próximas atividades.

A equipe poderá posteriormente:

```
Problema
   ↓
Pesquisa
   ↓
Produto
   ↓
Sprint
   ↓
Desenvolvimento
   ↓
Teste
   ↓
Feedback
   ↓
Melhoria
```

Assim, o GitHub passa a funcionar como um **registro real da evolução do produto**.
